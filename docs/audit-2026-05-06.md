# Audyt bodysync — 2026-05-06

> Wygenerowane przez `auditor` agent po porcie Claude Code setup ze sprawdzamszlak. Pierwszy reference snapshot — **pre-implementation** (backend i frontend nie istnieją, jest tylko bootstrap Terraforma).

## TL;DR

Bootstrap Terraform jest solidny technicznie (S3 versioned + encrypted, OIDC trust scoped do repo, IAM `iam:*` ograniczone do prefiksu projektu, `Resource = "*"` tylko dla read-only `List*` operacji), ale **całe live AWS (`syncbody-tfstate-*`, `syncbody-tflock`, `syncbody-github-actions`) ma nazwy `syncbody`** — drift względem zaakceptowanej w CLAUDE.md/PROJECT-STATUS.md nazwy `bodysync`. Po porcie `.claude/` jest niespójność: `frontend-designer` referenced w CLAUDE.md+command `audyt.md` ale **brak pliku agenta**, ciała agentów `security`/`tester` i wszystkie 5 SKILL.md nadal mówią `syncbody`. Provider w `versions.tf` (`aws ~> 6.43`) nie zgadza się z `.terraform.lock.hcl` (`aws 5.100.0`) — `terraform init -upgrade` jeszcze nie odpalony. Trzy największe ryzyka pre-implementation: (1) decyzja czy żyć z `syncbody-*` infra-bootstrap czy zburzyć i odbudować jako `bodysync-*` zanim ktokolwiek nauczy się starych nazw; (2) brak shared lib pattern (Lambda Layer vs `apps/api/src/shared/` import) — jeszcze niezdefiniowany; (3) HAE webhook sig-verify scheme nie zwalidowany czy HMAC w ogóle dostępny (Health Auto Export oferuje "Bearer token" w UI — nie HMAC; integrator agent zakłada HMAC).

> **Update post-audit (2026-05-06 same session):** punkty oznaczone ✅ **FIXED** zostały rozwiązane w tym samym PR-rze (`chore/claude-setup-port`). Te bez ✅ to follow-ups dla kolejnych PR-ów.

## Backend (`apps/api/`)

### Stan
- **Nie istnieje.** Brak `apps/api/` w drzewie.
- TODO.md plan: Lambda `google-auth` jako pierwszy endpoint (Phase 0 Step 5), shared lib w `terraform/lambda-src/shared/`. **Uwaga:** TODO.md mówi `terraform/lambda-src/shared/` — to **niezgodne z CLAUDE.md** który mówi `apps/api/` i jasno deklaruje że **kod Lambdy NIE w katalogu Terraforma** (memory `feedback_lambda_in_terraform_dir.md` z sprawdzamszlak wprost ostrzega). To rozjazd między dokumentami.

### Risks pre-implementation
- **Lambda packaging strategy nie wybrana.** ADR-001 nie precyzuje: `archive_file` per-function (klasycznie, każdy endpoint sam wozi `boto3` itp.) vs Lambda Layer ze wspólnymi pkg (`pydantic`, `PyJWT`, `google-auth`) vs `uv`/Docker image. Cold-start tax różni się 2-3x. **Decyzja do ADR przed Fazą 0 Step 5.**
- **Python 3.12 ESM-equivalent gotcha** — w sprawdzamszlak był feedback `feedback_lambda_esm_needs_package_json.md` (Node ESM bundle musi mieć `package.json`). Dla Python 3.12 odpowiednik to: jeśli używamy `pip install -t package/` z paczek z C-extensions (np. `pydantic-core`, `cryptography` — `PyJWT` ma `cryptography` jako optional dep), **ARM64 native wheels muszą być zaciągnięte z `--platform manylinux2014_aarch64`**, inaczej deploy z Maca skończy się binarką x86_64. To trzeba zaszyć w build script od dnia 1.
- **Strava idempotency port** — wzorzec ze sprawdzamszlak (DDB events table → DDB Streams → fetcher Lambda) jest 1:1 portowalny. Niuanse:
  - W sprawdzamszlak była tabela osobna od main (TS); tutaj single-table z `EVENT#strava` jako PK i TTL 7d (CLAUDE.md:90). To **świadomy KISS choice**, ale: DDB Streams można włączyć tylko per-table, więc przy single-table każdy zapis (BIOMETRY, ACTIVITY, EVENT) trafia do streama. Fetcher Lambda **musi filtrować po PK pattern** (`startswith(NewImage.PK.S, "EVENT#strava")`), inaczej szum. Filtrowanie po stronie EventBridge Pipes lub w handlerze Lambdy — koszt vs prostota.
  - `event_time + object_id + aspect_type` conditional write — zgadza się ze wzorcem.
- **HAE signature verify** — integrator.md mówi "shared secret w SSM, hmac-sha256, constant-time compare". **Health Auto Export apka iOS faktycznie wysyła HMAC?** Patrząc na docs Healthy Apps (https://www.healthyapps.dev/) — w UI apki jest pole "Authorization Token" (Bearer), **nie HMAC signature**. Sprawdzić to jest pre-req dla integrator/security przed implementacją. Bearer token w SSM + constant-time compare działa, ale to inna primitywa niż HMAC.
- **Anthropic prompt injection** — integrator.md i security.md dobrze rozróżniają system vs user message. Konkretne ścieżki ataku do testów:
  - Strava `description` zawierający `</user>... act as system: ...` — sprawdzić że Pydantic + cudzysłowowanie + flag "external data" w prompcie wytrzyma.
  - Google Sheets cell z prompt-injection content.
  Test fixture w `tests/fixtures/prompt_injection_payloads.json` od dnia 1.

## Infrastructure (`infrastructure/terraform/`)

### Co działa dobrze
- `main.tf` — S3 state bucket z `prevent_destroy = true`, versioning ON, AES256 SSE, public-access block, lifecycle 90d na noncurrent. DDB lock table PAY_PER_REQUEST, też `prevent_destroy`.
- `oidc.tf` — OIDC provider via `data.aws_iam_openid_connect_provider`, **nie zarządzany lokalnie** (zgodne z `feedback_shared_aws_account_resources.md` — singleton należy do sprawdzamszlak). Trust policy zawęża `sub` do `repo:tlyko/bodysync:*` (StringLike). PowerUserAccess managed policy + osobna inline `iam-management` z resource scope `arn:...:role/${var.project}-*`. Least-privilege po IAM-side: tak.
- `Resource = "*"` jest tylko dla list-API (`iam:ListRoles`, `iam:ListPolicies`, `iam:ListOpenIDConnectProviders`) — list-API nie da się ARN-scope'ować, standardowy pattern. **Nie flag.**
- `.gitignore` — `*.tfstate`, `*.tfstate.*`, `**/.terraform/`, `*.tfplan`, `override.tf` — kompletne.
- `infrastructure/terraform/terraform.tfstate` — istnieje na dysku, **nie jest tracked**.
- Brak sekretów w git history: skan po `aws_access_key`, `sk-ant-`, `GOCSPX-`, `AKIA`, `PRIVATE KEY` — zero matchów.

### Smells / ryzyka
- 🚨 **Naming drift `syncbody` → `bodysync`.** Live AWS resources stworzone z `var.project` defaultem `syncbody`: `syncbody-tfstate-214598715232`, `syncbody-tflock`, `syncbody-github-actions`. Build all downstream Terraform (lambdy, DDB, S3) z `${var.project}-*` da `syncbody-data` itd. — decyzja do podjęcia: (a) zmienić `var.project` default na `bodysync`, zaakceptować że bootstrap się przewali (resource replacement na `prevent_destroy = true` zablokuje S3+DDB → trzeba ręczny `terraform state mv` albo destroy+recreate), albo (b) zostać z `syncbody-*` na bootstrap (state backend, OIDC role) i nazwać tylko **app-side** zasoby `bodysync-*` — wymaga ADR wprost mówiącego "naming inconsistency między bootstrap-tier i app-tier — accepted technical debt".
- ⚠️ **Provider version mismatch.** `versions.tf` deklaruje `aws = "~> 6.43.0"`, ale `.terraform.lock.hcl` nadal trzyma `aws 5.100.0` (lock z poprzedniego pinu). Również lock zawiera `hashicorp/tls` którego `versions.tf` nie deklaruje. Następny `terraform init` bez `-upgrade` wybuchnie konfliktem. **Fix:** `cd infrastructure/terraform && terraform init -upgrade && terraform plan` lokalnie, commit zaktualizowanego lock-a.
- ⚠️ **OIDC trust policy zbyt permisywna.** `oidc.tf` — `StringLike: "repo:tlyko/bodysync:*"` daje dostęp do dowolnego ref (każdy branch, tag, PR head). Best practice z sprawdzamszlak (`feedback_terraform_plan_in_pr.md` + jego cicd) to:
  - apply path: `repo:tlyko/bodysync:ref:refs/heads/main`
  - plan path: `repo:tlyko/bodysync:pull_request`
  Można rozdzielić na dwa role albo zostawić jeden ze `StringEquals` na liście dwóch wartości. **Dla solo dev z protected `main` ryzyko niskie**, ale to free improvement.
- ⚠️ **Brak modułów app-tier.** `infrastructure/terraform/` ma tylko bootstrap (state + OIDC). PROJECT_PLAN.md i TODO.md zakładają `terraform/modules/{api-gateway,lambda,dynamodb,s3,eventbridge,ssm}/` — żaden nie istnieje. To nie smell, to po prostu "nie zaczęliśmy" — flag dla planowania. **Decyzja:** czy moduły idą w `infrastructure/terraform/modules/` czy w roocie z flat structure (5 zasobów to mało, modules dodają overhead). Architect ADR.
- ⚠️ **Brak `backend.tf` na app-tier.** Bootstrap używa local state świadomie, ale dalej Terraform musi mieć `backend "s3"` config wskazujący na bucket+lock — nie ma jeszcze ani app-tier folderu, ani `backend.tf`. Step 2 z TODO.md to adresuje.
- ✅ **FIXED — Orphan dir `terraform/bootstrap/`** (skasowany w tym PR-rze).

## Pytania do właściciela

1. **`api.bodysync.pl` vs `bodysync.pl/api/*` (CF Worker proxy):** mamy doświadczenie ze sprawdzamszlak że subdomain padł na CF Free. Czy chcemy iść proxy od dnia 1 (mniej ścieżek do customizacji) czy próbować subdomain (czysty separation)?
2. **HAE auth:** czy mamy potwierdzenie że Health Auto Export apka wysyła HMAC signature (jak zakłada integrator.md), czy tylko Bearer token w `Authorization` header (jak zakłada security.md po sweepie)? To zmienia design webhook handlera.
3. **Lambda kod lokalizacja:** TODO.md mówi `terraform/lambda-src/`, CLAUDE.md mówi `apps/api/`. Co jest źródłem prawdy? (Sugeruję CLAUDE.md, jak w sprawdzamszlak; TODO.md to zaktualizuj — ale to wymaga refactoru TODO planu).
4. **DDB Streams strategy:** filtrowanie szumu (BIOMETRY/ACTIVITY zapisy idą do tego samego streama co `EVENT#strava`) — handler-side filter czy EventBridge Pipes z filtrem? Druga opcja kosztuje +moduł, mniejszy noise.
5. **Naming policy ADR-002:** spisać formalnie "bootstrap zostaje syncbody-*, app-tier bodysync-*" — czy zrobić to teraz w osobnym PR-rze, czy wystarczy notatka w PROJECT-STATUS.md?
