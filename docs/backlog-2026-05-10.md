## Executive summary

**Gdzie jesteśmy (Sprint 0-9 zamknięty 2026-05-09):**
- Solidny **read-only data pipeline**: Apple Health (13 metryk biometr.) + Strava (activities + streams) + Google Sheets (training plan) → DDB → React dashboard z 7 tabami.
- **Reactive AI advisor** z RAG (139 przepisów Lidla/Biedronki) — owner pyta, dostaje odpowiedź, używa ad-hoc.
- **Mobile-responsive** dashboard z bottom nav, prototype 1:1 port — visual polished.

**Jeden mental model który spaja całą diagnostykę:** bodysync to dziś **passive log viewer**. User otwiera, scrolluje liczby, zamyka. Konkurencja (Whoop, Strava Premium, MacroFactor) zbudowała wokół tych samych danych **decision tools**: composite scores ("co dziś robić"), proaktywne push notifications ("recovery niski, easy day"), shared narratives ("tydzień: 4 treningi cel 3 ✓"), logbooki feedback loop ("ostatnie back squat 100kg × 6, dziś próbuj 102.5"). Wszystkie wymagają **tych samych danych które już mamy w DDB**.

**Cztery architektoniczne ruchy które unlockują 80% diagnostyki:**

1. **TDEE foundation (BMR/Mifflin-St Jeor + activity multiplier)** — bez wzrost/wiek/płeć w schema profilu, wszystkie cele kcal/makro lecą z hardcoded defaults a advisor gada ze średnich populacyjnych. Najtańszy single-PR fix który unlock'uje sensowną comparison vs target i adaptive TDEE downstream.
2. **Composite scores + narrative cards** — zamiast 13 raw StatCardów pokaż 3 syntezowane ("Recovery 78%, Forma +12, Cel makr 65%"). Minimal effort, transformative UX.
3. **Push channel (Telegram już deployowany w PR #130)** — daily morning brief + weekly recap + anomaly alerts + energy balance ("undereating!" / "+0.6kg/tydzień"). Owner nie musi otwierać appki. Aktywuje "active consumption" model.
4. **Logbook = pierwszy input UX surface** — bodysync jest ⅓-tenantowy ale 0% interaktywny (poza ProfileTargetsForm). Workout logbook lub meal log dodaje retention loop, daje advisor kontekst "co user faktycznie robi".

**Co NIE robić w najbliższych 3 sprintach (anti-bloat):**
- Garmin Connect direct (deferred per owner 2026-05-09 — Apple Health syncuje OK)
- Native iOS app / watchOS (multi-week effort, solo dev poza scope)
- Per-meal logging full system (rozsadza schema, advisor już ma kcal_in z HAE)
- Bundle code-split (152KB gzip jest akceptowalne pre-Sprint 12+)
- syncbody→bodysync rename (destructive, low business value)
- DDB CMK / requirements --require-hashes (compliance trigger nie aktywny)

## Strategiczne decyzje przed startem (do owner'a)

Pytania których odpowiedzi zmieniają kierunek backlog'u:

1. **Priorytet recovery score formuły** — własna heurystyka (HRV+sen+RHR+body_fat z arbitralnymi wagami) czy próba reverse-engineer Whoop/Oura algorithm? Decyduje czy B1 to S+M (heurystyka) czy M-L (kalibracja vs Whoop reference).

2. **Daily brief: tylko Telegram (owner) czy też in-app + Weronika kanał?** — Weronika może nie mieć Telegrama (sprawdź). Bez tego B2 dotyczy tylko ownera, parity dla pary wymaga in-app notification UI (B10).

3. **Workout logbook scope** — minimal "wpisz ile zrobiłeś" (text z RPE) czy full Hevy-style (per-set table z weight/reps progress)? Pierwszy = M effort, drugi = L effort.

4. **Per-meal logging vs status quo HAE-only** — czy chcesz aktywnie logować śniadanie/obiad/kolacja? Jeśli tak (B9), to dodatkowy input surface dla pary. Jeśli nie, polegamy na MyFitnessPal/Fitatu → HAE → DDB pipeline (już działa).

5. **PWA inwestycja (C1)** — pójście w PWA + web push otwiera "Add to Home Screen" + offline cache + native-feel. Cena: ~12-18h Sprint. Alternatywa: pozostać web-only, użyć Telegram jako jedyny push channel.

6. **Couples emphasis** — jak ważne jest że bodysync jest "dashboard pary"? Jeśli to USP (B8 + A3 priority), to inwestujemy w couples-specific features. Jeśli to coincidence że jesteście 2-tenantowi, idziemy single-user heavy features (B1+B2+B3 first).
