## 2. Smelle

### Architecture

- **ARCH-1 (🟡)** `infrastructure/terraform/cloudwatch.tf:86-128` — `module "telegram_notifier"` siedzi w **cloudwatch.tf**, nie w main.tf. Wszystkie inne 13 Lambdas są w main.tf. ADR-003 mówi "jeden moduł per service" + "tematyczne pliki". Telegram-notifier to subscriber CloudWatch alarm SNS, więc współistnienie z metric filter ma logikę — ale break'uje konwencję "Lambdas w main.tf". Rozważ albo move do main.tf, albo split na osobny `telegram.tf` z metric filter + alarm. Dziś jeden nowy reader szuka "telegram_notifier" w main.tf i nie znajdzie.
- **ARCH-2 (🟡)** `apps/api/handlers/advisor_chat/handler.py:99-369` — single handler dispatchuje POST / GET / DELETE. POST flow zajmuje 240 LOC (lines 130-369), GET/DELETE są wydzielone do `_history_handler.py` (113 LOC). Mix patterns: 50% kodu w handler.py, 50% w `_history_handler`. Naturalna refaktoryzacja: wydzielić `_post_handler.py handle_post_chat()`, zostawić w handler.py tylko JWT verify + 4-way dispatch (~60 LOC). Owner: tak, single-handler dispatch dla 3 methods rozjazd jest, ale dispatch jest cienki — prawdziwy zaduch to ciało POST. Wydziel POST i będzie ładnie.
- **ARCH-3 (🟢)** `apps/api/handlers/advisor_chat/_history_handler.py` underscore prefix — jedyna taka konwencja w całym `handlers/`. Inne handlers nie używają (mają `service.py`, `schemas.py`, `rag.py`). Pythonowo `_` mówi "private", ale to publiczne callable importowane przez `handler.py:42-45`. Lepiej `history_handler.py` (bez podkreślnika). Marginalne.
- **ARCH-4 (🟡)** `apps/api/handlers/advisor_chat/schemas.py:200-214` `CachedPlan` to **duplikat** z `handlers/plan/schemas.py`. Komentarz mówi expressly "fix Sprint 5 PR #4 — cross-handler import crashował Lambda runtime bo per-handler zip". Działa, ale to dług. Sprawdzenie nowych Lambdas (telegram, activity_suggestion) nie pokazało cross-handler importów, więc problem ograniczony do tego jednego miejsca. Trzy ścieżki: (a) shared/schemas.py dla cross-handler typów; (b) skrypt buildowy include'ujący "extra packages" w zip; (c) zostawić duplikat z explicit comment (obecnie wybrane). Sensowne.
- **ARCH-5 (🟢)** `apps/web/src/components/Dashboard.tsx` (874 LOC) — top-level komponent który nadal rośnie. Tabs są w `SidebarNav` + per-tab views w `components/dashboard/`, ale Dashboard.tsx orchestrate state. Brak unit test `Dashboard.tsx`. Test gap.

### Security

- **SEC-1 (🟢)** **Sekrety w git history:** sweep `git log -p -S 'sk-ant-' -S 'GOCSPX-' -S 'aws_access_key'` — czysto. Jedyny match `sk-ant-` jest w `service.py` komentarzu `# Anthropic API key prefix sk-ant-api03-`. Anthropic/Google secrets nigdy nie wpadły. Dobrze.
- **SEC-2 (🟢)** **`terraform.tfstate` w bootstrap/** — pliki istnieją lokalnie (`infrastructure/terraform/bootstrap/terraform.tfstate*`) ale `.gitignore *.tfstate` poprawnie matchuje (`git check-ignore -v` confirmed). Nie są commitowane. ✅
- **SEC-3 (🟢)** **IAM PK isolation** wszędzie poprawnie wyegzekwowane — każda Lambda ma `Condition: ForAllValues:StringLike dynamodb:LeadingKeys = ["USER#*"]` (lub dedicated prefix `STRAVA_OAUTH_STATE#*` / `EVENT#strava`). Jedyny wyjątek: `module.advisor_chat` `Sid: DDBReadRecipes` (main.tf:622-627) **bez Condition** — explicit udokumentowany w komentarzu z odpowiednim defense w kodzie (`rag.py` literal `:pk = "RECIPES"`) + test regression. Akceptowalne.
- **SEC-4 (🟢)** `advisor_chat` dostał `dynamodb:BatchWriteItem` + `dynamodb:DeleteItem` (main.tf:578-583) pod LeadingKeys USER#* — wystarcza dla `delete_chat_history`. IAM scope poprawny: PK isolation pilnuje że hard delete nie wyjedzie poza USER#{id} nawet jeśli handler ma bug. ✅
- **SEC-5 (🟡)** **Anti-injection schema sync:** `schemas.py:31-34` `_FORBIDDEN_CLOSING_TAGS` lista 6 tagów (`user_message`, `today_context`, `conversation_history`, `retrieved_recipes`, `training_plan`, `recent_activities`) **w pełni** matchuje 6 bloków używanych w `service.build_chat_messages` i opisanych w `system_prompt.txt` (sekcja ANTI-INJECTION). Brak driftu po PR #144 (dodanie recent_activities zostało zsynchronizowane z regex). ✅
- **SEC-6 (🟡)** `service.py:557` `sport_type=str(row.get("sport_type") or "Other")` — Strava `sport_type` jest user-controlled (custom workout types), ale wpada do prompt jako data inside `<recent_activities>` block. Anti-injection w system_prompt traktuje całość bloku jako data. Trim do 80 chars dla `name` (`RECENT_ACTIVITIES_NAME_MAX_LEN`), ale **sport_type bez trim** — Strava custom enum może być długi. Niski risk, defense in depth byłaby explicit `[:32]`.
- **SEC-7 (🟢)** Health Auto Export webhook signature verify: handler.py:1-15 + service `resolve_user_from_bearer` używa `hmac.compare_digest` na SSM secrets per-user (tomek + weronika). ✅
- **SEC-8 (🟢)** Throttling per route — API GW module ma global throttle + `POST /api/advisor/chat` override (cost-protect Anthropic). ✅ Brakuje per-route na `POST /api/auth/google` (JWKS fetch + crypto cost) — wskazane w komentarzu, ale nie zaimplementowane. ## 3. Ryzyko techniczne (30-day horizon)

1. **`advisor_chat/handler.py` urośnie nad ~450 LOC** przy nadchodzących sprintach (np. tool_use, streaming responses, multi-day history). Każda nowa funkcjonalność w POST flow = zaduch. Rekomendacja: extract `_post_handler.py` zanim Sprint 11 doda kolejną sekcję do POST flow.
2. **Cross-handler `CachedPlan` duplicate** w `advisor_chat/schemas.py` — jak doszłaby trzecia para handlerów potrzebujących shared schema (np. nowy chat handler + plan handler refactor), zaczyna się problem N×N duplikatów. Sygnał do wprowadzenia `apps/api/shared/schemas/` z importem allowlist-em w build.py.
3. **Dashboard.tsx 874 LOC** — kolejne 2-3 sprinty UX dorzucą ~200 LOC i będzie 1000+ z trudnym do testowania orchestration state. Refactor: useReducer + per-tab `useTabXYZ` hooki, albo Zustand store.
4. **DDB ACTIVITY query bez SK range** w `service.load_recent_activities:518` — używa `query_by_pk USER#{id} sk_prefix="ACTIVITY#"` + Pythonowy filter po `start_date`. Dla aktywnego usera (100+ activities w roku) cost: 1 RCU per 4KB = 100 items ~3-5 RCU per chat turn. Nie krytyczne dla 2-user MVP, ale skalowalność: dodać GSI z SK=start_date lub zapisywać `ACTIVITY#{YYYY-MM-DD}#{strava_id}` żeby `begins_with` wycinał już w DDB.
5. **Telegram bot_token rotation** — brak procesu. Jeśli token wycieknie, owner musi: BotFather → revoke → SSM put-parameter → re-deploy? Lambda czyta SSM przy każdym invocation (no cache), więc rotation = put-parameter wystarczy. Doceniam (no cold-start cache w telegram_notifier:114).

- **Anti-injection schema staying in sync** — PR #144 dodał `recent_activities` do system prompt **oraz** do `_FORBIDDEN_CLOSING_TAGS` regex. Drift, którego owner się obawiał, **nie wystąpił**. ✅
- **`apps/web/src/api.ts` jeden `request()` helper** — wszystkie 12 endpoint wrappers przechodzi przez ten helper, więc fix PR #146 (ApiError(-1) wrap dla TypeError) działa dla całego API. ✅ Dobry przykład pure-helper compounding zysk.
- **IAM PK isolation defense-in-depth** — wszystkie 14 Lambda mają explicit Condition LeadingKeys, jeden documented exception dla RECIPES PK z code-side guard + regression test. Wzorzec do utrzymania.
- **CloudWatch cost guard end-to-end** — metric filter → SNS → telegram_notifier Lambda → bot. Real-world resilience improvement nad email subscription (Gmail auto-unsub story). Smoke verified 2026-05-11 07:41-07:42 UTC: ALARM 🚨 + OK ✅ delivery, Lambda invoke 386ms cold start + 30ms warm.
- **Test coverage handlers 100%** + 317 backend tests + 147 frontend tests. Solidne foundation.
- **`shared/dynamo.batch_delete`** (PR #145) — najprostsza możliwa implementacja (boto3 batch_writer context), z explicit komentarzem o limits + idempotency. Jest jedynym callerem dla DDB DeleteItem w batch (single new helper, sole use site). ✅
- **Bootstrap separation** — `infrastructure/terraform/bootstrap/` z `prevent_destroy` na state bucket + lock table. SSE AES256 + lifecycle expire-noncurrent 90d. ✅

## 5. Konkluzja — 3 najpilniejsze rzeczy

### 1. Extract `_post_handler.py` z `advisor_chat/handler.py` → `architect` + `implementer`
**Why now:** handler.py 369 LOC, asymetria z `_history_handler.py` 113 LOC (GET+DELETE). POST flow dorzuca ~30 LOC co PR (rec_activities, plan, RAG). Sprint 11 doda kolejne. Po extract: handler.py ~80 LOC (JWT + dispatch), `_post_handler.py` ~280 LOC. Czytelność solo-dev po 3 miesiącach przerwy = priorytet KISS w CLAUDE.md.
**Subagent:** `architect` na decision (shape post-handler API + naming bez podkreślnika), `implementer` na delivery.

### 2. Ujednolicić telegram_notifier do `main.tf` lub split `cloudwatch.tf` na 2 pliki → `aws-infra`
**Why now:** `cloudwatch.tf:86-128` zawiera Lambdę telegram_notifier. ADR-003 i konwencja "Lambdas w main.tf" jest złamana w jednym miejscu. Onboarding-cost: nowy reader (lub nowy Claude session) szuka "telegram_notifier" w main.tf i nie znajdzie. Tani fix, jednoznaczny pozytywny effect. Opcja A: move modułu do main.tf z subsection nagłówkiem "Sprint cost-guard SNS subscriber". Opcja B: split na `telegram.tf` (Lambda + SNS sub + permission) + zostawić cloudwatch.tf z metric filter + alarm + topic.
**Subagent:** `aws-infra`.

### 3. Web component test coverage — dla `RecipeCard`, `ChatInput`, `RecipeModal`, `WeightChart` → `tester` + `frontend-designer`
**Why now:** 4 komponenty interaktywne (recipe selection, input validation, chart rendering) bez dedykowanych testów. Każdy regression na frontendzie kosztuje run Playwright + manual smoke. Lekkie unit testy (vitest + RTL) <100 LOC each, dadzą 50% confidence boost przy refactorach UI. Dashboard.tsx i LoginScreen mogą czekać — orchestration value < interactive component value.
**Subagent:** `tester` (delivery), `frontend-designer` (decyzja co testować — interaction surface vs visual diff).
