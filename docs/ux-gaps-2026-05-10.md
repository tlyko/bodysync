# UX/UI gap audit — bodysync frontend (2026-05-10)

Audyt jakościowy stanu obecnego dashboardu, podzielony na 10 obszarów. Każdy obszar zawiera 2-4 obserwacje (mix friction + delight gaps). Cel: zidentyfikować luki bez planowania implementacji.

## 1. Dashboard overview

- Header zawiera tylko "Dashboard" + dzień tygodnia (PL_DATE.format), brak personalizacji typu greeting "Dzień dobry Tomek" lub time-of-day awareness ("rano" / "wieczór"). User po loginie nie widzi nic emocjonalnego, tylko siatkę liczb.
- "Aktywności (tydzień)" card pokazuje counter, ale visual-only (per kod: "klikalne via sidebar tab, owner kliknie sam"). Wygląda actionable ale nie reaguje na klik — punkt frustracji który powtarza się dla podobnych metrycznych kafelków.
- Brak top-of-page narrative typu "Twój dzień: HRV 78 ms (powyżej 7d średniej), masz w planie Trening B" — Dashboard pokazuje raw metryki bez syntezy. User musi sam łączyć kropki.
- Recovery box ma 2x2 mini-stats (HRV / Sen / RHR / Body fat) jako raw values — żaden composite "Recovery score 0-100" mimo że dane do niego są w DDB. To największy single UX gap dostępny z istniejącymi danymi.

## 2. Aktywności tab

- Lista 20 ostatnich + connect CTA, ale **brak per-activity drilldown** — kliknięcie ActivityRow nic nie robi. Streams JSON są w S3 (Sprint 4) i kompletnie nieskonsumowane przez UI; HR zones, splity per km, elevation profile czekają.
- Brak filtrów (sport_type / date range / distance > X) — przy 100+ activities owner będzie scrollować. Search po nazwie też brak.
- Brak agregacji weekly/monthly ("ten miesiąc: 15 treningów, 120 km biegania, 45 km roweru") — pojedyncza Aktywności (tydzień) na Dashboard to wszystko.
- Brak map preview mimo że Strava zwraca `summary_polyline` w `/activities` payload — nawet thumbnail leaflet/google static tile zwiększyłby visual appeal o 10×.

## 3. Ciało

- Sparkline na każdym StatCard ale **brak overlay vs target/baseline** — user widzi liniię ale nie wie "to powyżej czy poniżej moich norm?". Trend % 7d-vs-7-14d pokazuje ruch, nie poziom.
- WeightChart 30d to raw daily weight — noise z hydratacji/glikogenu daje +/-0.5 kg dnia na dzień. Brak overlay smoothed line (EMA α=0.1) który MacroFactor robi pod hasłem "true weight".
- 6 metryk w jednej siatce (HRV / Sen / Kroki / Spalone / RHR / Body fat) bez logical grouping — Recovery (HRV+RHR+Sen) i Activity (Kroki+Spalone) to 2 różne intencje, mieszają się wizualnie.
- Brak sleep stages breakdown (core / REM / deep) mimo że HAE wysyła te wartości i fallback `asleep = core+rem+deep` jest w PR #46. Single liczba "asleep 7.5h" gubi insight "tylko 1.2h deep".

## 4. Odżywianie

- NutritionDonut żyje na **Dashboard overview**, nie na Odżywianie tab — user wchodzi w "Odżywianie" i widzi 4 makro StatCardy bez głównej wizualizacji. Inwersja lokalizacji.
- TodayMetricStatCard pokazuje "0 kcal" gdy HAE nie wysłał (PR #115 decision) — semantycznie OK ale wizualnie nie odróżnia "0 spożyte celowo" od "brak danych" — oba wyglądają jak liczba zero z malutką sparkline z poprzednich dni.
- Brak **comparison vs target** mimo że ProfileTargets API jest gotowe — "1200/2000 kcal · zostało 800" to single zdanie który zmieni Odżywianie z log-viewera w decision tool. Ring/bar visual jak Apple Fitness rings byłby naturalny.
- Brak meal logging UI w ogóle — kcal_in z HAE to suma dnia, nie per-meal. User nie może zapytać "co dziś jadłem", advisor też nie wie kontekstu o żywności.

## 5. Przepisy AI / Chat

- ChatScreen po pierwszym otwarciu pokazuje pustą thread — **brak suggested prompts** ("Zaproponuj śniadanie wysokoproteinowe", "Co zjeść po treningu", "Czego mi dziś najbardziej brakuje w diecie"). New user nie wie co wpisać.
- 24h DDB TTL + brak `GET /api/advisor/chat/history` (backlog #21) = **refresh strony = lose UI state**. To największy in-session friction — user zamknie tab, wróci za 2h, traci kontekst rozmowy.
- RecipeCard → modal pokazuje ingredients/instructions ale **brak save/favorite/dodaj-do-listy-zakupów** — przepis ma value tylko podczas tej rozmowy, nie persists w pamięci usera.
- Brak onboardingu czat ("To asystent z biblioteki przepisów Lidla i Biedronki — pyta co chcesz zjeść, dostosuje do Twoich makro"). New user nie wie że ma RAG do dispozycji.

## 6. Plan Treningowy

- Tabs A/B/C/D z dropdown weeks per group to dobra navigation, ale **read-only view** z Google Sheets — brak logbook input. Owner po treningu nie ma gdzie kliknąć "zrobione".
- Brak per-set actuals (faktyczne wagi × reps × RPE vs plan) — Hevy-style logger byłby naturalnym fit, dane idą do DDB jako `WORKOUT_LOG#{date}#{exercise}` i karmią advisora kontekstem ("ostatni back squat 100kg × 6").
- Brak progress over time per ćwiczenie — chart "back squat 4x6 — trend wagi" wymaga logbook'a above (#23 backlog dotyczy timestampów).
- Brak per-day assignment — owner sam wybiera który Trening dziś. Heurystyczny hint na Dashboard ("ostatni done = Trening A z poniedziałku, dziś sugeruję B") jest tani.

## 7. Onboarding

- LoginScreen → Google → Dashboard — **zero guided setup**. New user (lub Weronika przy pierwszym logowaniu) nie widzi "podłącz HAE webhook na telefonie / podłącz Strava / wpisz training sheet ID".
- Empty states działają (np. "Brak aktywności. Połącz konto Strava w zakładce Aktywności") ale rozproszone per tab. Single setup checklist na Dashboard po pierwszym loginie ("3/4 done — została konfiguracja Plan Treningowy") byłby clearer.
- Brak tooltipów "co to za metryka" — HRV vs RHR vs Recovery, nie każdy user (zwłaszcza Weronika która ma niższy zaangażowanie w domain) wie co znaczą liczby.
- Brak pre-login "what is bodysync" landing screen — strona logowania to tylko logo + Google button. Brak feature pitchy / screenshot grid.

## 8. Notifications

- **Brak in-app notifications w ogóle** — żaden surface dla "advisor reply ready", "training plan updated", "weekly recap available", "cost-guard alarm".
- Push notifications (web Push API) niezaimplementowane — daily morning brief 07:00 (jeśli powstanie) nie ma kanału do usera poza Telegramem.
- Telegram bot (PR #130 in-progress dla cost-guard) to backend channel dla owner-only — brak parity dla Weroniki ani fan-out per user-set preferences.
- Cost-guard alarm trafi tylko do Telegram, nie do UI — owner używający tylko web nie zobaczy nigdy alertu.

## 9. Mobile delight

- iPhone bottom nav (PR #114) z safe-area-inset + stat-grid 2-col na 390px+ — solid baseline. Ale **brak gestures**: swipe między tabami, pull-to-refresh, long-press na StatCard dla detail.
- Brak haptic feedback (`navigator.vibrate(10)` na tap StatCard / przycisk wysłania chat) — tani polish który różnicuje "responsywny dashboard" od "native-feel app".
- Brak share-card export — weekly recap, longest workout, weight trend → PNG generowany Canvas API frontend, download/share na Telegram/IG. Strava-style hook, viralność.
- Brak iOS Shortcuts integration (single endpoint `/api/widget/today` zwracający JSON z 3-4 stats — Apple Shortcut user wstawia w widget). Daje glance na lock screen bez native app.
- Brak watchOS / iOS native widget — to wymaga natywnej app (poza scope), ale Shortcuts powyżej to 90% UX value w 5% effort.
- Hardcoded dark theme — brak `prefers-color-scheme` autoswitch ani `rem`-based sizing dla iOS Text Size accessibility.

## 10. Couples + comparisons + narratives

- 2-tenantowy single-tenant z założenia (para), ale **UI nie eksponuje partnerki** — owner widzi tylko siebie. Brak switcher (siebie ↔ Weronika) ani shared dashboard.
- Brak head-to-head comparisons ("Tomek 8500 kroków, Weronika 11200 — w tym tygodniu wygrywa Weronika"). Apple Activity sharing to robi już dla pojedynczych ringów, bodysync ma 13 metryk biometrycznych.
- Brak shared streaks ("5 dni z rzędu oboje wykonali plan", "30 dni partnerka logguje wagę"). DDB `STREAK#daily#both_logged_workout` counter to 50 LOC backend + 20 LOC frontend.
- Brak "lepiej niż wczoraj / tydzień temu" insights — `trendPct` w biometry.ts liczy 7d delta ale UI pokazuje tylko liczbę %, nie narrative ("Twój 7d HRV +5%, dobry kierunek").
- Brak anomaly alerts ("RHR 3 dni z rzędu 8 bpm wyżej niż baseline — może choroba?", "Waga +1.2 kg w tygodniu, hydration noise czy nadwyżka?"). Z-score per metryk to ~30 LOC analytics, push przez Telegram bot.
- Brak narrative weekly recap ("Tydzień: 4 treningi (cel 3 ✓), waga +0.2 kg (utrzymanie ✓), HRV stable, sen 7.2h avg") — single Anthropic call cron'owy z biometry+activities last 7d, persist do DDB `RECAP#{week}` i frontend tab "Recaps".
